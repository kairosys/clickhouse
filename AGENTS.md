# Agent Guide — ClickHouse workspace

## What this is
A self-contained ClickHouse deployment, not an application repo. There are two top-level directories:

- `data/` — live server state (databases, users, config) mounted into the pod as a hostPath volume (`/var/lib/clickhouse`). This directory tree is **authoritative and actively mutating** whenever a real cluster runs; treat file edits here as data operations, not code changes.
  - `metadata/*.sql` are ClickHouse DDL files (e.g. `default.sql`, `system.sql`) generated by the server from `ATTACH DATABASE ... ENGINE = Atomic`. Do not edit to change schema — use SQL via the HTTP/native interface instead; edits may be overwritten on restart.
  - `preprocessed_configs/` is machine-generated output of config merging; editing it has no stable effect (regenerated before each read). Edit `/etc/clickhouse-server/config.xml` or a `.d/*.xml` override in the image instead.
  - `status`/`uuid`/top-level files are runtime markers (`data/status` contains `PID:`, `Started at:`, `Revision:`). Ignore for source work.
- `k8s/` — Kubernetes manifests to run ClickHouse as a StatefulSet (namespace `default`, ports HTTP `8123` / native `9000`), backed by hostPath `/mnt/workspaces/clickhouse/data`. Files: `clickhouse-secret.yaml`, `clickhouse-configmap.yaml`, `clickhouse-statefulset.yaml`.

## High-signal facts an agent would otherwise guess wrong
- **Credentials live in the working tree, untracked.** `k8s/clickhouse-secret.yaml` holds `CLICKHOUSE_USER=clickhouse` and the password as plaintext `stringData`. `.gitignore` excludes `k8s/*-secret.yaml` and it has never been committed — keep it that way (`git add -f` would leak it). If it ever lands in a push, rotate it.
- **`data/` is gitignored** — `.gitignore` excludes the entire `data/` directory. Do not commit files here.
- **HostPath path quirk (Linux paths on a macOS working tree).** The StatefulSet references host node path `/mnt/workspaces/clickhouse/data`, which does not exist as-is under `data/` here (`/Users/kevin/Workspaces/clickhouse/data`). If you apply these manifests to a real cluster, that path must be created and populated on the target node; otherwise ClickHouse starts with an empty data dir. Do **not** create symlinks from `/mnt/workspaces/clickhouse` inside this repo expecting it to map correctly — mount/host paths are resolved on the *node running the pod*, not in your filesystem.
- **Image is `clickhouse/clickhouse-server:latest`** (unpinned) plus `CLICKHOUSE_DB=langfuse`. If you apply `kubectl apply` against a cluster, prefer pinning to a specific digest/tag and confirm the volume contains this server's data, else a fresh `latest` will start empty.
- **Live schema is in the `default` database, not `langfuse`.** The manifest sets `CLICKHOUSE_DB=langfuse` and the README shows `langfuse.traces`, but the live data dir (`data/metadata/`) has only `default`, `information_schema`, `system` — the langfuse tables (traces, observations, scores, analytics_*) live in `default`. Query against `default.*` or verify the DB name in `data/metadata/` before writing SQL.
- **ConfigMap mount** — `k8s/clickhouse-configmap.yaml` creates ConfigMap `clickhouse-configmap`, mounted as `memory-limits.xml` into `/etc/clickhouse-server/config.d/`. If you need custom server config, add files to this ConfigMap.
- **Resource limits** — requests: 250m CPU / 512Mi memory, limits: 1 CPU / 2Gi memory.
- **Namespace is `default`** in all manifests (no explicit `metadata.namespace` field — relies on the current context default).
- **No build/test/lint lifecycle here.** There is no Makefile, Dockerfile, CI workflow, package manifest, or test suite for this workspace itself — it is configuration + runtime data only. The only relevant verification command when changing these files is a Kubernetes apply/diff such as:
  ```
  kubectl diff   -f k8s/clickhouse-statefulset.yaml
  kubectl apply  -f k8s/
  ```

## Working with live data safely
These files come from a running server (`data/status` shows e.g. `Revision: 54514`). While a ClickHouse instance backed by this directory is up, the engine holds file locks and writes continuously. To inspect without corrupting state, attach a read-only client rather than editing on-disk files:
```sh
clickhouse-client --host <pod-ip> --user clickhouse -p <password-from-secret> \
  "SELECT name FROM system.databases"
```
